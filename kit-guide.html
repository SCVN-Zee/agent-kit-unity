01 / Start with intent

What are you trying to do?

Write or change Unity code

Start with code conventions. Add Odin for Inspector work when it is installed.

Review without changing anything

Start with code review. It brings in the relevant policy and surface checklists.

Name or organize content

Use asset conventions for filenames, folders, importer intent and hierarchy names.

Recreate a reference feature

Use reference feature to carry the reference through observation, adaptation and proof.

Handle a special setup or target

Luna separates authoring, compatibility review and export settings. Codebase Memory is explicit tooling setup, not a prerequisite.

For user-invocable skills, use /skill:aku-… in OMP/Pi, $aku-… in Codex, or /aku-… in Claude Code. A skill is an instruction document the agent reads—not a separate worker process.

02 / The mental model

One baseline. Different paths for different jobs.

Rules: what must hold, or what to read

The core rule stays active. The code and asset rules are short signposts. Tier rules add project-specific requirements.

Skills: the focused handbook

A skill contains a protocol, policy references, examples or a helper. The agent loads the relevant pieces instead of reading the whole kit for every task.

Core guidance applies throughout. C# authoring goes through the code bridge to code conventions; report-only work enters code review; naming work goes through the asset bridge. Odin, Luna compatibility and Supercent layout are conditional additions, not mandatory steps in one pipeline.

The overview groups the two convention bridges with their handbooks. Reference-feature, explicit tooling setup and the remaining Luna parts appear below. No shipped rule or skill is omitted from the catalog.

04 / How the pieces refer to each other

Policy ownership is more useful than a giant link graph.

A reference means “read this for its part of the answer.” It does not mean “launch another agent” or “execute every linked skill.” The maps highlight the main routes; each card contains the full named cross-reference evidence.

Example: a required Animator field

Code conventions owns whether the reference is required, how it is wired and how runtime code drives the Animator.

Odin supplies the Inspector presentation. On Luna, Luna conventions adds the stripping guard without stripping the field.

Example: a named prefab

Asset conventions distinguishes the prefab filename from names inside its hierarchy.

Review can inspect affected serialized references. Neither naming policy nor a source compile proves the prefab is correctly wired.

Luna adds three distinct responsibilities

Authoring asks “How should I write this?” Compatibility review asks “What may break in export?” Build check asks “Are these export settings correct?” None is proof of a successful playable build.

The reference-feature path: one record from observation to proof

This is a conceptual summary of its eight phases, grouped into four readable stages—not four replacement gates.

  1. 1. Contract & observeIdentify the requested feature and record observed cues without inventing hidden behavior.
  2. 2. Map & challengeFind local owners, lifecycle exits, conflicts and the smallest viable adaptation.
  3. 3. Plan & implementPreserve cue IDs, acceptance criteria and existing gameplay contracts.
  4. 4. Verify & deliverProve behavior, rendered fidelity and integration separately; restore probe state.

The packet links these stages. Media, planning and verification helpers are used only if available and relevant. --analyze stops before edits; it does not claim runtime verification.

05 / What actually gets installed

Same source. Four host layouts.

kit/ is the maintained source. The installer copies it to OMP or projects it into Pi, Codex and Claude Code. OMP remains the default; select another host with --target pi|codex|claude. This guide describes instructions, not a runtime enforcement engine.

Oh My Pi (OMP)

.omp/skills/aku-*/SKILL.md contains skills. Rules live under .omp/rules/.

Always-apply rules provide standing guidance; the other rulebooks carry task descriptions and file patterns. rule:// and skill:// references point to relevant guidance.

Pi

.pi/skills/aku-*/SKILL.md uses native skill discovery. .pi/APPEND_SYSTEM.md carries core guidance and compact task/tier routing.

.pi/rules/ contains referenced documents—not a native rules engine. URI references become explicit project-relative paths. Start Pi from the trusted project root; reload after installation changes.

Codex

.agents/skills/aku-*/SKILL.md uses native skill discovery. A managed section in root AGENTS.md provides startup guidance while preserving surrounding user content.

.codex/aku-rules/ holds on-demand references, not automatically loaded rules. Root AGENTS.md and .agents/skills/ are shared discovery surfaces: independent ownership does not mean host-exclusive visibility.

Claude Code

.claude/skills/aku-*/SKILL.md uses native skill discovery. .claude/rules/aku-project.md provides project startup guidance.

.claude/aku-rules/ holds on-demand references. The installer does not modify CLAUDE.md, settings or MCP configuration. Loading still depends on project trust and host configuration.

Use the checkout commands in the Codex/Claude target guide; release installs require an archive containing these targets. Restart a trusted host session after installation. File generation and skill discovery do not prove startup loading, invocation or Unity runtime correctness.

Tier selection, overrides and installer boundaries
Supercent install
Detected from Assets/Supercent/.
Luna install
A Luna signal (luna.json, Assets/Luna/, or a Luna/Playworks package) plus a playable target. The target-specific aku-project.json boolean lunaPlayable wins; otherwise the branch name must contain playable. Explicit --tier luna can include it.
Install ≠ apply
The installed files are available; each skill still checks task relevance. Luna review and build check describe broader runtime context signals than installer auto-selection. Do not treat every detection check as identical.
Independent ownership
Each target reads its own optional marker: .omp/aku-project.json, .pi/aku-project.json, .codex/aku-project.json or .claude/aku-project.json. Markers are user-owned; there is no cross-target fallback. The odin override selects policy, not actual DLL/API availability.
No automatic tools
The kit does not register specialist agents, MCP servers or providers. The host agent discovers Editor capabilities. Installing Codebase Memory guidance does not run its setup.

Evidence: tier detection · Pi target · kit entry guidance

Each target has an independent checksum lock; locks track ownership, not skill activation. Codex/Claude uninstall preserves edited entries and their lock records, exiting 2 for incomplete removal. Force never deletes the whole root AGENTS.md or bypasses structural safety. See the host guide for installation and conflict handling. See the README for installation and lifecycle commands.

Source caveats: where the current documents disagree

Luna review verification: Luna review’s protocol step 6 says to run tests and save dirty scenes, while its report-only section forbids Editor-state changes. Common review’s protocol forbids saving user state and requires separate authorization for fresh verification. This guide does not resolve that contradiction or authorize a save. Clarify verification scope before acting.

References to retired helpers: Luna Animator/prefab guidance mentions common Animator and prefab skills, but those standalone skills are not in the current payload. Use available Editor capabilities; do not assume a missing skill was installed.
